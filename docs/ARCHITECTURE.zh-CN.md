# 架构

[English](ARCHITECTURE.md) | **简体中文**

Feishu Codex Bridge 是一个本机消息通道与任务编排服务。飞书负责远程交互，
Codex Desktop 仍然是实际执行环境。

![架构流程](images/workflow-zh-CN.svg)

## 组成部分

### 飞书机器人私聊

接收用户消息、附件和 Card 2.0 操作，并展示任务首页、进展快照、消息队列、
定时任务、健康状态和完成通知。

### 本机 Bridge

当前 macOS 用户的 LaunchAgent 负责消费飞书事件，并处理：

- 用户、私聊和项目白名单校验；
- 自然语言及精确命令路由；
- 事件去重和持久化暂存；
- 后续消息队列和本机定时任务；
- 附件保留和进展脱敏；
- Card 2.0 创建与更新。

### Codex Desktop app-server

Bridge 通过本机 Unix WebSocket 连接 Codex。飞书创建的任务会出现在 Codex Desktop，
Desktop 创建的任务也可以进入 Bridge 任务首页。这个 Socket 不会通过 TCP 或公网暴露。

### 项目白名单

新任务只能进入 `workspaces` 中明确列出的绝对路径。自然语言别名只用于路由，
不会授权访问其他目录。

## 任务生命周期

1. Bridge 校验飞书用户和私聊会话。
2. 解析目标项目或已有 Codex 任务。
3. 通过共享本地 app-server 提交回合。
4. 过滤进展信息并生成飞书卡片。
5. 回合结束后释放任务写入权，让 Desktop 可以重新打开。
6. 其他进程仍持有写入权时，后续消息进入持久化队列等待。
7. 任务完成、失败或需要人工处理时发送通知。

这个所有权模型可以避免多个进程同时写入同一个任务。Desktop 同步默认保持被动，
不会自动跳转或接管任务窗口。

## 本机状态与恢复

事件执行前会去重。事件、待处理操作、定时计划和任务映射都会持久化到本机，
因此 Bridge 重启后不会静默丢失已接收的工作。单实例锁用于避免两个本机进程同时
消费同一个飞书应用。

## 为什么不要求 MCP

MCP 用于向 Codex 暴露工具和数据源。这个项目解决的是另一类问题：作为后台服务接收
飞书事件，并把它们传输给本机 Codex 运行时。增加 MCP 不能替代飞书应用创建、用户配对、
LaunchAgent 或项目授权。

Codex Skill 或 Plugin 可以让安装和恢复更方便，但底层仍然需要安装并运行这个 Bridge。

## 信任边界

- 飞书凭据保存在本机 `lark-cli` Profile。
- Codex 凭据继续由 ChatGPT Desktop 管理。
- 远程回合不能批准额外权限。
- 进展信息离开 Mac 前会进行摘要和脱敏。
- 能访问配对飞书账号，就应视为能访问全部白名单项目。

部署建议见 [SECURITY.md](../SECURITY.md)。
